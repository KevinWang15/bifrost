When to stop and how to recover

Stop progression on a failed/incomplete migration, wrong artifact/version, data loss or decryption failure, authorization regression, repeated crashes, or failure of the working OpenAI/OpenRouter critical paths. For performance, error rate or log lag, use the baseline thresholds and observation duration agreed before the window. If verification cannot finish before the last safe rollback-start time, the deployment owner chooses the pre-agreed restore or extended-outage path.

Decision pointRecovery action
Before migration startsIf preparation/backup gates fail and the old database has not been changed, restore the old deployment configuration as needed, start the exact old services and reopen after smoke checks. No database restore is needed solely for an aborted pre-migration preparation.
After migration, before public trafficKeep maintenance active and stop all 2.0/application writers. Preserve failure evidence. Restore every database and the matching configuration/object recovery point from the coherent backup; verify all restores succeed before booting the exact old image and Portal configuration. Test old schema/data/decryption, ingress, inference and SSO, then resume traffic and jobs. Account for any test writes discarded by restore.
After real writes resumeDrain and stop writes again, record the new cutoff, preserve a full copy of the failed 2.0 state and object references, then restore the old recovery set. Post-backup logs, budgets, users/keys and other changes will be lost from the restored live state. Reconcile them from preserved evidence using a reviewed procedure; there is no verified automatic reverse migration. Do not replay provider calls blindly because they may incur duplicate charges or tool effects.
Recovery acceptanceAll stores must reach the same recovery point before any writer restarts. Verify historical content and permissions, exact old artifact, Portal/SSO, inference and reporting. Preserve new-only objects for reconciliation rather than deleting them during rollback. Record actual outage, data-loss interval and recovery results.
Restore is the recovery boundary. A tag change or image-only downgrade is not the rollback procedure. 2.0 merges OAuth tables and drops five old oauth_configs columns. Old and new writers must never share the migrated schema. If zero post-cutover data loss is required, design and rehearse an additional reconciliation strategy before scheduling; the current restore rehearsal does not provide it.
